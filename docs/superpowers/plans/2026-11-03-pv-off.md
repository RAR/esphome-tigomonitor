# PV Off Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let the owner turn the array's output off and on from the monitor (web UI, API, Home Assistant) with the CCA's own `0x0B00 00`/`01` frame, held across the hourly re-assert, restarts, TAP bring-ups and standby takeovers.

**Architecture:** A header-only `PvSwitch` in `tigo_master.h` owns the PV state, the immediate send, retries and the reply check; `Housekeeping` takes its session byte from it. `MasterCore` carries the state, learns it from the bus while standing by, and reports it through a save callback. The Pi persists it in `<state_dir>/pv.json` and exposes it on `/api/master`, `POST /api/master/pv`, MQTT and a new Bus master page; the ESP32 exposes an ESPHome switch.

**Tech Stack:** C++17 header-only protocol code (host-tested with `tests/host/*.cpp`), the Pi daemon (cpp-httplib, nlohmann/json, libmosquitto), ESPHome (Python codegen, ESP-IDF), `app.html` (vanilla JS, Playwright tests in `site/test/`), bash e2e scripts against `linux/tools/mock_tap.py`.

**Spec:** `docs/superpowers/specs/2026-11-03-pv-off-design.md`

## Global Constraints

- The PV frame is command `0x0B00` with one byte: `00` = off, `01` = on. Name them `PV_OFF = 0x00`, `PV_ON = 0x01`; never write a bare byte.
- The TAP's reply is `0x0B01` carrying the same byte (roof capture: `0x0B00 [01]` → `0x0B01 [01]`, `~/tigo-protocol-analysis/docs/ROOF_STEADY_STATE.md:72`).
- While off is held, `01` is never sent: not hourly, not in a bring-up, not at start or takeover.
- Only `0x0B00 00` and `0x0B00 01` are new to the guard; nothing is added to or removed from the never-send list.
- Retry an unconfirmed switch every 5 s, up to 5 times, then flag it unconfirmed; keep re-asserting on the hourly tick.
- A standby that's standing by never sends; its switch is read-only. A heard state wins over a device's own at takeover.
- `POST /api/master/pv` answers 403 while no web password is set.
- `mqtt.pv_switch` defaults to false; with it false no switch is announced and commands are ignored.
- UI copy, verbatim: confirm "Turn the array's output off? This is not rapid shutdown."; banner "PV output is off, turned off from <device> at <time>".
- `/api/master` stays out of `site/screenshots/fixtures.mjs` (Pi-only); don't edit `CHANGELOG.md` (deferred to the release pass).
- Never run sudo; builds and tests run in Docker: `docker run --rm -v "$PWD":/src -w /src tigod-dev sh -c '...'`.
- After any `app.html` change: `sed -n '/<script>/,/<\/script>/p' components/tigo_server/web/app.html | sed '1d;$d' > /tmp/app.js && node --check /tmp/app.js`.
- Commit messages follow `.claude/skills/shipping-tigo-changes`; no attribution trailers.

## Rulings made while planning

- **Persistence in `<state_dir>/pv.json`, not `settings.json`.** A settings save rebuilds the bus master (a ~2 s bus gap) and reconfigures MQTT, and a heard state is state, not a setting. Cost if wrong: one file to fold into settings later.
- **"Unconfirmed" is a flag in the PV status, not a `Fault`.** `Fault` holds one value; PV must neither mask nor clear `second_master` or `lease_refused`. `/api/health` reports it as a problem either way. Cost if wrong: a rename.
- **An unreadable `pv.json` counts as off held,** logged at error and reported on `/api/health`; a missing file is on. That fails toward the anti-goal (no PV on by accident), and the banner makes it visible. Cost if wrong: lost production until the owner presses On.
- **On the ESP32 the switch is a view:** `restore_mode` is forced to `DISABLED`, and the state lives in the component's own preference, so the switch's restore can't act as a fresh command at boot.

## Review Focus

1. A second off or on request while a send is still unconfirmed: the latest wins, with one retry series, not two interleaved ones.
2. A daemon restart mid-retry, after off was asked but before the TAP confirmed: it comes back off and sends `00` first.
3. A corrupt or truncated `pv.json`: off held, an error logged, a health problem, and no `01` sent.
4. The Home Assistant switch toggled on a standby that's standing by: the switch snaps back to the heard state, and nothing is sent.
5. A command (API or MQTT) during the moment a settings save is rebuilding the bus master: the state is kept in the store, and the new master sends it.

**Interfaces:**
- Produces:
  - `static const uint8_t PV_OFF = 0x00, PV_ON = 0x01; static const uint16_t CMD_SESSION_REPLY = 0x0B01;`
  - `enum class Allow { yes, bench_only, startup_only, optimizer_write, pv_off, never };`
  - `bool may_send(uint16_t cmd, const Bytes &payload, bool bench, bool startup = false, bool writes = false, bool pv_off = false);` (`Allow::pv_off` → `pv_off || startup`)
  - `class PvSwitch`:
    - `PvSwitch(bool off, bool hourly, uint32_t now_ms)`: `hourly` = PvSwitch sends the hourly re-assert itself, because no housekeeping does; `off` true queues `00` at once.
    - `void set_off(bool off, uint32_t now_ms)`: queues the byte at once and resets retries.
    - `bool off() const`, `uint8_t value() const`.
    - `Request due(uint32_t now_ms)`: cmd 0 when nothing is due.
    - `void on_reply(const Request &req, bool ok, const Frame &reply, uint32_t now_ms)`, for every `CMD_SESSION` request from any source.
    - `bool confirmed() const`, `bool unconfirmed() const` (after 5 retries), `int last_sent() const`, `int last_reply() const` (-1: none).
    - `static const uint32_t RETRY_MS = 5000, RETRIES = 5, HOURLY_MS = 3600000;`
  - `Housekeeping::set_pv(const PvSwitch *pv)`: its session frames use `pv->value()`. With `pv->off()`, the bring-up sends `00` once and drops the `01` after it, and the opening and hourly `01` become `00`.
  - `next_request(..., Housekeeping *, Queries *, PvSwitch *pv = nullptr)`: `pv->due()` goes first, before the lease, so a switch goes out in the next slot.
